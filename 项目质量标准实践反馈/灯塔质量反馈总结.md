# 前端二开质量问题共性场景总结与SOP优化建议

> 数据来源：本项目（Demo_DT）2026-08-14 ~ 2026-08-19 期间共 20 个 AI 协作会话的实际对话记录（问题反馈、返工来回、最终修复方案）。
> 目的：对应【Web端开发】B/S架构二开项目标准SOP「阶段4 Web端质量自检」及「阶段2 前期资料准备」，把本项目实际暴露的质量问题沉淀为共性场景，反哺团队质量标准。

## 一、总体情况

- 20 个会话中，约 60%（12 个）存在"同一问题反复 2 轮及以上"才收敛的情况，集中在**布局/样式还原**与**组件参数化**两类。
- 多数返工不是"做不到"，而是**第一版没有先量、先确认，就直接改**，导致方向或数值猜错，来回试错消耗了大量沟通轮次。
- 未发现功能性缺陷被交付到 TB 验收阶段（问题都在开发内部闭环），但反复轮次本身就是**人天成本**，值得在 SOP 里提前拦截。

## 二、共性问题场景与根因

### 1. 布局/样式还原反复返工（占比最高）
**现象**（均为实际用户反馈原文）：
- "但是现在下班部分和上半部分就有重叠了啊，根本没有动态调整下半部分的占比"
- "动力的那一个是和生产的同一行啊" →"没有实现"→"还是没有实现"→"你弄错了吧"（同一问题反复 4 轮）
- "没有实现一样宽啊"
- "这个柱状图像是被压缩了" / "数值并不是在每个柱状紧跟着的上方，而是在整体柱状图对应的著装的上方"

**根因**：CSS 数值（gap、flex-basis、column-gap 等）凭经验设定，没有结合"容器实际渲染像素宽度"实测；`flex:1`（basis:0%）与"按内容自然高度 hug"的诉求混用，导致布局在不同数据量/不同模块下表现不一致。

**建议纳入 SOP**：
- 阶段3 开发规范增加一条硬性要求：**涉及"是否同一行/是否等宽/是否溢出"类还原，改动前后都要用 `getBoundingClientRect` 等方式实测容器与内容像素尺寸，不能仅凭代码走查或截图肉眼判断**。
- 阶段4 自检 Checklist 增加"关键容器实测记录"项，作为布局类需求的验收证据之一。

### 2. 组件参数化/复用范围不足
**现象**：
- "有没有办法使该部分的宽度不要顶死根据内容最长的部分进行统一长度呢"（柱状图组件宽度写死）
- "我说了是加参数控制，不要影响到其他页面的柱状图"
- "这个的gap能不能参数传一下" / "这个padding-left也需要传" / "这个高度是全部写死了吗，能不能单独只给柱状图"

**根因**：跨模块复用组件在首版实现时只覆盖了当前模块的数据形态，没有预留关键样式（宽高/间距/最大值）的对外参数接口，导致每次新模块接入都要"回头加参数"。

**建议纳入 SOP**：
- 阶段2 需求功能清单模板增加"组件复用范围"字段：明确该视觉元素会被几个模块复用、哪些维度（宽高/间距/颜色/最大值刻度）在不同模块间存在差异。
- 阶段3 开发规范：**凡跨 ≥2 模块复用的组件，首版实现即默认暴露核心样式 props（不写死数值），而不是等第二个模块接入时才补**。

### 3. 需求理解未先确认、方向性返工
**现象**：`e168b55e` 会话中"生产/动力是否同一行"这一需求，AI 先改错方向、用户纠正后又改错一次、最终第 4 轮才通过实测 column-gap 找到根因，共耗时约 47 分钟、7 轮对话。

**根因**：对"是否同一行"这类结构性需求，AI 没有先复述/确认设计意图（如引用设计图具体位置或数据结构），就直接动手改代码，试错成本从"确认成本"转嫁成了"返工成本"。

**建议纳入 SOP**：
- 阶段3 开发规范：结构性/位置类需求变更，先用一句话复述理解（引用设计稿坐标或既有数据结构），获得确认后再改代码，尤其是修改会牵涉数据结构（如 `moduleConfig.js`）时。

### 4. 交互状态互斥/联动遗漏
**现象**：
- "下拉框有个问题，假如我选择时段，打开了一个下拉框，再点击区域的下拉框，时段的应该关掉了啊"
- "我点击侧边栏的按钮后，在点击下拉框，出现侧边栏的功能没有取消"

**根因**：多个独立交互组件各自管理自身开关状态，缺少"同类元素互斥"或"跨组件联动"的统一设计，需求单阶段也未列出这类交叉场景。

**建议纳入 SOP**：
- 阶段2 需求表模板增加"功能互斥/联动矩阵"字段（列出哪些 UI 元素之间存在互斥或联动关系）。
- 阶段4 自检 Checklist 中"整体链路走查"细化为**必须显式测试列出的互斥/联动组合**，而不是走一遍主路径就算完成。

### 5. 编译/运行时错误未在提交前自查
**现象**："打不开页面，似乎是报错了"；`Vue warn: Property or method "getCaerma" is not defined on the instance`（方法名拼写错误）。

**根因**：改动后未做最基本的本地热更新 + 控制台无报错检查就同步给用户。

**建议纳入 SOP**：
- 阶段4 前置条件里的"本地 npm run build 打包通过"之外，补充**"每次改动即时自检"级别的最小项**：热更新后控制台 0 Error/Warning，作为交付每个小任务前的默认动作，而非等到整体自检阶段才统一查。

### 6. 敏感信息/安全意识
**现象**：接入 LLM 接口时，API Key 曾被要求"有没有别的办法加密也行啊，或者不要放这个文件哇，别人一看就知道了"（`public/config.json` 明文密钥）。

**建议纳入 SOP**：
- 阶段2 数据接口文档模板明确：涉及密钥/敏感凭证一律通过 `devServer.proxy` + 环境变量注入，不落地到前端可读文件/仓库。
- 阶段4 Checklist 增加"敏感信息扫描"项（搜索 `sk-`、`Bearer `、明文 token 等特征字符串）。

### 7. 总结/沟通类输出格式与预期不符
**现象**：多次要求"根据我今日提交...总结做了什么"后又追加"不要全是代码，说功能啊""你写的详细一点啊，不要全是什么文件，写修改了什么完成了什么，功能描述"。

**根因**：日报/总结默认以技术实现（文件、代码）表达，未对齐 TB/PM 更关心"业务功能"的沟通语言。

**建议纳入 SOP**：
- 阶段3"每日进度同步"环节固定输出模板：**功能点 + 完成效果**，技术细节（文件路径）作为附注而非主体，减少来回澄清。

### 8. 专项技术领域（WDP 3D 场景）知识沉淀不足
**现象**：模型高度/地形贴合、动画速度参数、样式来源等问题需要现场排查解释（"这个船速的感觉很快啊，有没有办法然他速度慢点""现在的 addParabola 样式在哪里修改"）。

**建议**：此类问题已在个人经验库中沉淀为可复用的排查方法（地形采样、Bound 播放、坐标系语义等），建议将 WDP 二开常见坑位整理为团队级 skill/知识库，避免同类问题在不同项目中重复试错。

## 三、SOP 优化建议汇总（可直接落地到相应阶段文档）

| SOP 阶段 | 现有内容 | 建议新增/细化 |
| --- | --- | --- |
| 阶段2 前期资料准备（需求功能清单模板） | 交互需求描述 | 增加"组件复用范围"字段、"功能互斥/联动矩阵"字段 |
| 阶段2 数据接口文档 | 接口地址与字段 | 明确密钥类信息的注入方式（proxy+环境变量），禁止前端明文 |
| 阶段3 AI Coding 开发规范 | 布局搭建/组件复用流程 | ①结构性需求先复述确认再改代码；②布局改动前后用实测像素校验；③跨模块复用组件默认暴露核心样式 props |
| 阶段3 每日进度同步 | 日报模板 | 固定"功能点+效果"表达顺序，技术细节作为附注 |
| 阶段4 质量自检 Checklist | 硬件兼容/UI还原/场景功能/数据有效性 | 增加：关键容器实测记录、功能互斥联动逐项走查、控制台0报错、敏感信息扫描 4 项 |

## 四、结论

本项目暴露的质量问题**集中在"确认不足就动手"和"复用/健壮性预留不足"两类共性场景**，均可通过在 SOP 阶段2/3 提前约束（需求表字段细化、开发规范硬性要求）和阶段4 补充自检项来源头拦截，从而减少同一问题的多轮返工，降低人天成本、提升首轮交付质量。
