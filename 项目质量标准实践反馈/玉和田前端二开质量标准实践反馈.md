## 二、逐项分析与反馈

### A. 交互时序竞争 / 模块互斥缺失

- **现象**：用户点击过快时，上一个交互（如人员轨迹 POI 弹窗）尚未删除，下一个交互（谈话按钮、今日轨迹、进度条）就已执行，导致弹窗残留；修掉弹窗残留后又暴露"镜头抢夺抖动"（多个交互同时抢占相机）。
- **根因**：多条交互链路（POI 弹窗、轨迹播放、镜头聚焦）各自独立异步执行，缺少统一的操作队列 / 串行化，也缺少防抖。模型类交互因走引擎自身管线不易复现，弹窗类交互走 51_web 事件链路更易暴露。
- **git 印证**：`3b9a1c0`「解决用户点击过快弹窗未关闭+镜头抢夺问题」是一次独立的专项修复提交。
- **共性场景**：凡是「打开 A 面板时 B 面板应收起 / 镜头切换互斥」的场景都可能触发，与 SOP 阶段 4 "关注功能之间的互斥/联动"直接对应。
- **对质量标准的反馈**：
  1. 现有 Checklist 只写了"关注互斥/联动"，**缺少可执行的量化判据**。建议新增：*快速连续点击（≥3 次/秒）任意可切换面板/POI，不得出现残留弹窗、镜头抖动或叠加*。
  2. 建议在框架层沉淀「场景操作串行化 + 交互防抖」的标准封装，作为二开脚手架默认能力，而非每个项目各自重写。

### B. 引擎坐标 / 高度基准不统一（掉地底）

- **现象**：无人机沿路径移动时高度突然掉到地底；静止时正常、一动起来就失效；反复多轮仍是"重置状态正常、播放即掉地底"。
- **根因**：对 `coordZRef` 语义理解不清——`surface/ground` 只在 `Scene.Add` 建模时按地形抬高一次，后续 `SetLocation` 用的是绝对海拔、不再按地形抬高；相对地表高度的数据用手动逐帧定位无法贴地。真实后端 GPS 数据自带绝对海拔无需换算，mock/相对高数据才需沿路径采样地形换算。
- **git 印证**：`b8b4bee`「优化模型绑定路径过程中抖动问题，替换为标准API」——最终以引擎标准 API（`App.Bound`）收敛。
- **共性场景**：所有"手动逐帧移动模型沿引擎地形路径"的功能（车/人/无人机轨迹播放）。
- **对质量标准的反馈**：
  1. 建议在需求/接口对接阶段（SOP 阶段 2）就**明确约定轨迹数据的高度基准**（绝对海拔 or 相对地表高度），并写入数据接入模板，避免开发期反复试错。
  2. 建议标准移动方案统一走引擎原生 `App.Bound`（沿贴地路径播放，高度由引擎保证），或用 `ProjectTerrainSampleAPI` 采样地形换算为绝对海拔后全程 `Altitude`，作为团队推荐实践写入 WDP 二开规范。

### C. 模型朝向 / 镜头参数缺乏基线

- **现象**：垃圾车/人员/无人机的模型朝向反 180°、需逆时针 90°、绑定路径倒着走；跟随视角反向、静态聚焦偏左/偏高，全靠肉眼反复"再转一点、再平一点、再远一点"。
- **根因**：模型初始朝向、跟随镜头、静态聚焦镜头的参数没有统一基线与命名约定，验证稿（html）与生产代码参数容易漂移（多次追问"两个文件参数一致了吗"）。
- **git 印证**：`镜头优化`（`1370367`/`19391b5`/`d006fe2`/`9b50fbe`）与 `seedid 替换`（`338bb6e`/`5eff05f`/`1b97ba3`/`a5587d7`）各出现 3~5 次独立提交，**量化印证该类返工强度高**。
- **对质量标准的反馈**：
  1. 建议每类模型建立**朝向/镜头参数基线配置**（初始 yaw、跟随相机 pitch/距离、静态聚焦相机），集中在配置对象里而非散落调用点。
  2. 建议约束"验证稿与生产代码单一数据源"：调参 html 直接从生产配置读参数，避免调完 html 再手工回填导致漂移。

### D. 播放器状态机一致性（播放 / 暂停 / seek）

- **现象**：暂停后再拖拽进度条、放手后模型不在对应位置；拖拽时进度条闪回一下再更新；拖拽到停止点附近模型回退点与路径对不上；无人机前端视频弹窗与进度条时间不同步。
- **根因**：引擎 `Bound` 无原生 seek，进度条用挂钟计时只更新 UI 不动模型，seek 需在松手时删旧 Bound、截子路径重建续播；播放/暂停/拖拽三态与 UI 时间、外部视频弹窗的联动点多，任一处状态未同步即对不上。
- **git 印证**：`45805d1`「进度条拖拽」、`5cb5a21`「无人机今日轨迹+播放条时间优化」。
- **对质量标准的反馈**：建议将「播放器类交互」列为独立自检项，明确覆盖矩阵：*{播放中、暂停中} × {拖拽 seek、点击 seek} × {模型位置、进度时间、关联视频}* 九宫格全部一致。

### E. 后端数据未就绪时的自验证手段

- **现象**：人员 POI 后端返回空，无法验证人员路径/播放效果，被迫先写假 POI 或借用车辆/无人机数据验证。
- **git 印证**：`7e38cac`「面板数据兜底」、`0dda184`「参数+弹窗修复」体现了对数据缺失兜底的持续处理。
- **对质量标准的反馈**：建议将「Mock 兜底 / 自验证数据」纳入标准交付要求——每类动态实体都应有一份可开关的 mock 轨迹，保证后端未就绪时前端仍能自检，且交付前确认 mock 已关闭（呼应 SOP 阶段 4"已切换到生产/类生产配置、Mock 关闭"）。

### F. 生命周期幂等 / 死代码清理

- **现象**：场景预热/重连后 `OnWdpSceneIsReady` 再次触发，引擎残留上一轮实体，直接重新 loadAll 导致 POI 重复叠加；此外存在未使用的导出函数需交付前清理。
- **git 印证**：`e5d399f`「修改新湖和进入场景无人机POI问题」、`4818cbc`「初始化清空场景」、`a1bff2b`「代码优化瘦身」。
- **对质量标准的反馈**：
  1. 建议新增自检项：*场景就绪回调必须幂等*——就绪回调开头先清理引擎残留实体并重置 JS 侧加载标记，再重新加载。
  2. 死代码清理：交付前核对导出函数的真实引用（"被导出 ≠ 被使用"），呼应 SOP 阶段 4"死代码/带病部署"要求。

### G. 推流 / 渲染稳定性（画面卡死、弹窗黑屏）

- **现象**：首次进入场景点击 POI 添加弹窗后，画面卡死在最后一帧（`30ea5ad`）；弹窗多次出现黑屏，反复修复（`fd42738`/`1307bf0`）。
- **根因**：WDP 库在 `Scene.ClearByTypes`/`FocusToEntities` 等命令期间会主动 `video.pause()` 重协商流但不自动 `.play()` 恢复；低分辨率恢复快、肉眼无感，4K+/弱解码硬件恢复慢到看似"卡死"。弹窗黑屏则与首帧渲染/背景样式相关。
- **共性场景**：高分辨率大屏、首次访问、切换场景/聚焦实体后的画面恢复；这类问题在开发机（低分辨率）不易复现，交付到大屏才暴露。
- **对质量标准的反馈**：
  1. 建议将"推流恢复兜底"（监听 `#streamingVideo` 的 `pause` 事件，被暂停立即 `.play()`）作为二开脚手架默认能力。
  2. 建议 Checklist 明确"必须在目标分辨率/目标硬件（而非开发机）复测一遍推流与弹窗"，呼应 SOP 阶段 5"部署后二次自检、防止网络/环境差异造成的表象差异"。

### H. 登录 / 路由 / 分辨率健壮性

- **现象**：登录后路由参数丢失（`852cb27`）；分辨率适配出现漂移需还原（`41cb8a1`）。
- **对质量标准的反馈**：建议 Checklist 增加"登录链路参数透传"与"目标分辨率 1:1 还原"两项基础健壮性检查。

## 三、建议纳入《项目自检Checklist》的新增检查项

以下为本项目实践提炼、建议补充进团队通用 Checklist 的条目（当前版本未覆盖或仅泛泛提及）：

1. **[交互]** 快速连续点击任意可切换面板/POI（≥3 次/秒），无残留弹窗、无镜头抖动、无实体叠加。
2. **[3D]** 所有动态实体轨迹的高度基准已在接口/需求阶段确认（绝对海拔或相对地表高度），并在移动全程保持一致（静止=运动高度一致，无掉地底）。
3. **[3D]** 每类模型的初始朝向与跟随/静态镜头参数取自集中配置基线，验证稿与生产代码参数一致。
4. **[播放器]** 播放/暂停 × 拖拽/点击 seek × 模型位置/进度时间/关联视频，九宫格状态一致。
5. **[数据]** 后端数据未就绪时具备 mock 自验证能力；交付前确认 mock 已关闭、指向生产配置。
6. **[生命周期]** 场景就绪/预热/重连回调幂等，重复触发不产生实体叠加。
7. **[代码]** 交付前核对导出函数真实引用，清理死代码。
8. **[推流/渲染]** 在目标分辨率与目标硬件上复测：切换场景/聚焦实体后画面不卡死、弹窗无黑屏。
9. **[健壮性]** 登录后路由参数正确透传；目标分辨率 1:1 还原无漂移。

## 四、可复用的验证方法沉淀

- **交互时序问题定位**：用 `el.__vue__` 拿组件实例，对可疑方法打补丁记录调用序，直接观察同一 tick 内的连环调用，比猜测冒泡路径更快。
- **3D 高度/坐标核对**：以引擎地形采样结果为准换算绝对海拔，不要靠肉眼截图判断掉地底与否。
- **推流卡死诊断**：DevTools Console 读 `#streamingVideo` 的 `paused/currentTime/readyState`，区分 WDP 内部 pause 未 resume、autoplay 策略阻挡、WebRTC 流问题三种根因。
- **大屏 1:1 分辨率还原验证**：用 headless Playwright `screenshot` 拍真实分辨率截图，绕开集成浏览器的物理窗口尺寸限制，避免"innerWidth 匹配即认为截图完整"的假阳性。

## 五、工程过程规范反馈（来自 git 提交记录）

除功能质量外，提交历史本身也反映出可优化的过程规范：

- **提交信息不规范**：存在多次提交信息仅为 `1` 的情况（如 `2810933`/`53fb702`/`5d32d25`/`f065bfb` 等），后续回溯问题、定责、生成变更记录都困难。建议约定最简提交规范（类型 + 简述，如 `fix: 修复快速点击弹窗残留`），呼应 SOP 阶段 4/7"每条反馈有出处、有修改记录"。
- **高返工模块集中**："镜头优化""seedid 替换"各出现 3~5 次独立提交，量化印证 C 类问题缺乏基线配置导致反复微调。建议将高返工模块的参数收敛到集中配置，减少提交次数与联调轮次。
