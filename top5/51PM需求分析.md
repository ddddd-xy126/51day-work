目前已完成飞书反馈数据抓取、AI分析、结果回填的接线验证，整条链路已实测跑通。

- AI侧：需要人工触发分析流程；

  当前唯一人工介入点：
  收到飞书提醒后，手动触发「抓取新反馈并分析」。
  距离真正的「新增反馈 → 自动分析 → 自动回填 → 通知审核」无人值守模式，还缺少自动触发机制。

方向二
[图片]
飞书中有多维表格自动化发送 HTTP 请求功能介绍，设想流程：
用户填写反馈
→ 飞书新增记录
→ 飞书自动化发送 HTTP 请求
→ 自动分析服务（读取反馈 + 组装SKILL规则和语料 + 调用本地大模型分析 + 提炼两句话）
→ 回写飞书
→ 人工 Review
详细流程如下

1. 用户填写反馈 → 飞书生成记录
   用户在飞书多维表格填写反馈。提交后，飞书新增一条记录，并生成唯一 record_id，用于后续读取这条反馈和回填分析结果。
2. 飞书自动化触发 → 调用自动分析服
   飞书检测到新增反馈后：

- 继续发送群消息通知；
- 同时通过 HTTP 请求调用自动分析服务，请求携带 record_id + table_id。
  告诉自动分析服务："有一条新反馈，需要执行需求分析。"

3. 自动分析服务：组装材料 → 交给本地大模型 → 拿到分析结果
   第一步：读取反馈内容
   根据 record_id 调用飞书接口，复用 feishu-client.js + fetch-new-feedback.js，获取这条反馈的完整字段（模块/问题描述/优先级/反馈类型等）。
   feishu-client.js = "怎么跟飞书打交道"的工具箱。里面就三个函数：拿授权令牌、读表里所有记录、改某一条记录的字段。它自己不做任何业务判断，纯粹是"敲门砖"。
   fetch-new-feedback.js = 一个只干一件事的脚本："把反馈表里所有记录拉下来，挑出『需求分析结果』还是空的那些"，相当于帮你从一堆反馈里，筛出"还没被分析过、需要处理"的那几条。
   两者关系：fetch-new-feedback.js 干活时调用 feishu-client.js 里"读表"这个函数去真正跟飞书要数据——feishu-client.js 是工具箱，fetch-new-feedback.js 是拿着工具箱去做一件具体事的人。
   第二步：组装材料
   把下面三样东西打包在一起：- 这条反馈的完整内容 - 需求分析 SKILL 的规则（五段式模板、判断标准、few-shot 范例）- 测试验收沉淀的语料（entry_map / impact_map / playbooks）
   注：SKILL 本身不是"执行的一步"，它只是规则文档，是打包进材料里、喂给模型的"作答说明书"。
   第三步：调用本地大模型完成分析
   把打包好的材料整体发给 51PM 已部署的本地大模型，模型照着 SKILL 的规则一次性产出分析结果：
   反馈内容 + SKILL规则 + 语料
   ↓
   本地大模型
   ↓
   问题分析 / 影响功能 / 用户诉求 / 原因分析 / 需求方案
   第四步：提炼两句话
   从模型输出的五段式结果里，提炼出「问题整理」+「方案推荐」（对应 SKILL 里产物 B 的规则）。
4. 自动分析服务回写飞书
   根据原始 record_id，复用 write-back.js，把两句话写回这条记录对应的两个字段：

- 需求分析结果
- 产品/解决方案简述
  write-back.js = 一个只干"写"这一件事的脚本：拿到一个 record_id + "问题整理"这句话 + "方案推荐"这句话，就去把这两句话分别塞进飞书表格那一行对应的两个字段（『需求分析结果』、『产品|解决方案简述』）。
  它内部也是调用 feishu-client.js 里"改记录"那个函数去真正操作飞书——跟 fetch-new-feedback.js 是同一个套路，只是一个负责"读"、一个负责"写"。

5. 负责人查看分析结果
   飞书表格中自动出现 AI 分析内容，负责人 Review、修改、确认。
